ESPECIFICACAO_POLITICAS_OPERACIONAIS_PERSISTENTES_V1
=====================================================

OBJETIVO
========
Criar na Biblioteca um sistema persistente de POLÍTICAS OPERACIONAIS.

A política serve como memória operacional do sistema.

Ela não representa um estado temporário como uma TAG.
Ela representa uma REGRA que deve acompanhar automaticamente o contexto onde estiver aplicada.

Exemplos:

TAG:
🎯 MAIS_CANDIDATAS
→ informa o que está acontecendo AGORA naquele slot.

POLÍTICA:
CENTRAL_2 exige assets transparentes
→ informa COMO aquele tipo de slot deve SEMPRE ser tratado.


=====================================================
PRINCÍPIO CENTRAL
=====================================================

A IA NÃO DEVE DEPENDER DE MEMÓRIA OU DE PROMPT PARA SABER REGRAS IMPORTANTES.

Quando um agente/MCP consultar ou operar um slot, o backend deve entregar automaticamente:

- dados do slot;
- preset;
- tags ativas;
- políticas aplicáveis;
- políticas herdadas;
- instruções operacionais relevantes.

Assim, a regra fica persistida no sistema e acompanha o trabalho.


=====================================================
O QUE A POLÍTICA DEVE PERMITIR
=====================================================

A política deve poder ser:

- criada manualmente pela UI;
- criada pelo MCP;
- editada manualmente;
- editada pelo MCP;
- ativada/desativada;
- removida/apagada;
- vinculada a um ou mais contextos;
- aplicada a projetos;
- aplicada a presets;
- aplicada a slots;
- futuramente aplicada a itens semânticos/universos/tipos;
- consultada automaticamente pelos agentes.

Não exigir deploy para criar uma política nova.


=====================================================
DIFERENÇA ENTRE TAG E POLÍTICA
=====================================================

TAG
---
Estado ou necessidade atual.

Exemplos:
🎯 MAIS_CANDIDATAS
👁️ REVISAR
⚠️ SCRIPT_MISMATCH
📤 THUMBS_UPLOAD_REQUIRED

Normalmente temporária.


POLÍTICA
--------
Regra persistente de operação.

Exemplos:
- QUAL_VOCE_PREFERE usa imagens crop-safe 4:3.
- CENTRAL_2 exige PNG/transparência real.
- EMOJI usa pistas isoladas, não uma cena completa.
- Nunca aprovar preview não materializado.

Normalmente persistente.

=====================================================
ASSOCIAÇÃO COM PROJETOS
=====================================================

Uma política pode ser aplicada diretamente a um projeto.

Exemplo:

scope: PROJECT
target_id: PROJ-ABC123

Quando qualquer agente entrar em qualquer slot daquele projeto,
essa política deve aparecer no payload.

Também deve ser possível criar políticas específicas para um slot:

scope: SLOT
target_id: <project_id>:<slot_id>


=====================================================
LEITURA AUTOMÁTICA NO SLOT
=====================================================

Toda leitura de slot pelo MCP deve retornar algo semelhante a:

{
  "slot_id": "scene-05-image-a",
  "preset": "QUAL_VOCE_PREFERE",

  "tags": [
    {
      "tag_key": "MAIS_CANDIDATAS",
      "emoji": "🎯"
    }
  ],

  "policies": [
    {
      "policy_key": "PRESET_QUAL_VOCE_PREFERE_4X3",
      "scope": "PRESET",
      "instruction": "As duas imagens devem funcionar em crop 4:3 e preencher bem o card."
    },
    {
      "policy_key": "PROJECT_VISUAL_QUALITY",
      "scope": "PROJECT",
      "instruction": "Evitar sujeitos pequenos ou com excesso de área vazia."
    }
  ]
}

O agente não deve precisar fazer uma segunda consulta para descobrir as políticas básicas.

A leitura passiva é obrigatória.

=====================================================
APRENDIZADO OPERACIONAL
=====================================================

A IA/MCP pode criar uma nova política quando detectar uma regra recorrente útil.

Exemplo:

Depois de vários projetos, a IA percebe:

"Retratos muito estreitos funcionam mal em QUAL_VOCE_PREFERE."

Ela pode criar:

policy_key:
QUAL_VOCE_PREFERE_AVOID_NARROW_PORTRAIT

scope:
PRESET

target:
QUAL_VOCE_PREFERE

instruction:
"Evitar assets verticalmente estreitos; preferir enquadramento que aceite crop 4:3 sem reduzir demais o sujeito."


A política passa a existir para os próximos projetos.

Isso cria aprendizado persistente sem depender de memória da conversa.


=====================================================
CONTROLE DE SEGURANÇA DO APRENDIZADO
=====================================================

A IA pode criar políticas livremente,
mas toda política deve guardar:

created_by
created_at
scope
target
instruction

E a UI sempre deve permitir:

- visualizar;
- editar;
- desativar;
- excluir.

Assim, o usuário continua com controle total.

=====================================================
QA GUIADO POR POLÍTICA
=====================================================

O QA deve receber automaticamente o asset_requirement do slot.

Exemplo:

preset:
CENTRAL_2

slot:
IMAGEM_PRINCIPAL

requirement:
transparent_subject


O QA valida:

- semântica correta;
- referência correta;
- requisito visual do preset;
- transparência quando exigida;
- crop 4:3 quando aplicável;
- ocupação do quadro;
- ausência de watermark/logo/texto indevido;
- resultado visual, quando existir.


Se falhar apenas no fit do preset:

NÃO APROVAR PARA AQUELE SLOT.

O asset pode continuar válido para outro uso compatível.


=====================================================
COLETOR GUIADO POR POLÍTICA
=====================================================

O Coletor também deve receber o requirement.

Exemplo:

CENTRAL_2:
buscar "Sasuke PNG transparent render"

em vez de:
buscar "Sasuke"

Exemplo:

QUAL_VOCE_PREFERE:
buscar imagem com composição/crop compatível com 4:3.

Exemplo:

FILME:
buscar objeto/pista visual isolada,
não screenshot completo da cena.


=====================================================
RELINK GUIADO POR POLÍTICA
=====================================================

O Relinker deve considerar:

SEMÂNTICA
+
PRESET
+
ASSET_REQUIREMENT

Nunca relinkar um transparent_option para um raster contextual só porque o objeto está correto.


=====================================================
POLÍTICAS APLICADAS AO PROJETO
=====================================================

Quando um projeto for criado ou receber roteiro:

1. identificar presets usados;
2. resolver automaticamente políticas PRESET aplicáveis;
3. aplicar políticas GLOBAL;
4. aplicar políticas PROJECT específicas;
5. aplicar políticas SLOT específicas;
6. disponibilizar tudo no payload dos agentes.

Não é necessário copiar fisicamente as políticas para cada projeto.

Pode ser herança dinâmica.

Se quiser congelar versão histórica da política usada,
registrar policy_id + policy_version na execução/QA.


=====================================================
VERSIONAMENTO RECOMENDADO
=====================================================

Opcional, mas recomendado:

version
supersedes_policy_id

Ao editar uma política importante,
preservar histórico da versão anterior.

Assim é possível saber qual regra estava ativa quando um projeto foi produzido.

UI DO SLOT
=====================================================

- o sistema acumula aprendizado operacional ao longo do tempo.
